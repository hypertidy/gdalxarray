gdalxarray

An xarray backend powered directly by GDAL

import xarray as xr
ds = xr.open_dataset(path_or_uri, engine="gdalxarray")

gdalxarray is a thin bridge between what GDAL can read (classic rasters, multidimensional arrays, and every virtual store GDAL knows about) and xarray’s labelled-array model. It is lazy by default, Dask-chunked on request, and carries CRS and CF time through.

Every code block on this site is run when the site is built, so what you see is what the current release does against the current GDAL. The small inputs are cuts of real public data kept with this repository, each with a script that rebuilds it from its source; the larger examples in the Gallery read public cloud stores, listed with their permanence on the Stores page.

Nothing has been read yet beyond the metadata and the coordinate arrays. Selecting and plotting pulls only the chunks needed:

sst = ds["sst"].isel(time=0, zlev=0)
fig, ax = plt.subplots(figsize=(9, 4.4))
sst.plot(ax=ax, cmap="RdYlBu_r", vmin=-2, vmax=32, cbar_kwargs={"label": "degrees C"})
ax.set_title(str(ds.time.values[0])[:10])
plt.show()

The same call works for a netCDF on a web server, a COG in a bucket, a multidimensional VRT, a kerchunk-Parquet reference store or an Icechunk repository: only the string changes.

Why this exists (and when to use rioxarray instead)

rioxarray is an accessor and backend built on rasterio. For a single GeoTIFF or a STAC item it is the mature, well-tested choice.

gdalxarray goes straight to osgeo.gdal. That matters when:

  • the data is N-dimensional: GDAL’s multidimensional API is exposed natively, with named dimensions, not only (band, y, x);
  • the path is a composition: /vsicurl/, /vsis3/, /vsizip/, vrt://, ZARR:, NETCDF:, classic and multidim VRT all nest;
  • driver and codec support should track GDAL: Zarr v3, kerchunk Parquet references, Icechunk, GRIB, HDF4/5 multidim.

Status

Active development; the API has settled but may change before 1.0. See the Changelog and the issue tracker.
